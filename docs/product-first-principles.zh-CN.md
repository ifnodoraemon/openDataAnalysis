# Open Data Analysis 第一性原则

更新日期：2026-06-22

这份文档定义本项目自己的产品第一性原则。它不是功能清单，也不是愿景口号；它用于判断后续取舍是否服务真实数据分析用户。

## 1. 用户要的是可信结论，不是漂亮过程

产品价值不来自“Agent 看起来很忙”，而来自用户能复核、能追问、能拿去决策的结论。

因此：

- 每个关键结论都应能追溯到数据源、口径、查询或计算依据。
- 当字段含义、时间粒度、join key、单位或指标口径不确定时，系统应暴露歧义，而不是生成完整但不可靠的报告。
- 报告优先回答业务问题；交互过程、工具调用和运行树只服务可解释性，不应喧宾夺主。

## 2. 数据源是产品核心，不是上传入口的附属品

真实用户的数据来自文件、数据库、对象存储和未来的业务系统 API。系统应把这些都看成一等数据源，而不是把 CSV 上传当成唯一正路。

当前原则：

- 文件上传适合一次性小中型分析和离线样本。
- PostgreSQL 连接先做 snapshot import，保证复现、审计和资源边界。
- 大型数据库对象默认不能无界导入；必须有明确行数上限、快照状态和截断提示。
- 未来 live query 应作为独立能力设计，不能混入当前 snapshot import 的语义。

## 3. 小、中、大数据走不同路径

同一个按钮不能假装所有数据规模都一样。

当前分层：

| 规模 | 行数 | 默认处理原则 |
|---|---:|---|
| small | < 10,000 | 尽量做精确 schema 和统计画像 |
| medium | 10,000 - 99,999 | 混合画像，保留足够统计事实 |
| large | 100,000 - 999,999 | 采样画像，明确标注估计字段 |
| xlarge | >= 1,000,000 | 默认受限快照，优先要求用户缩小表、视图或时间范围 |

这不是为了限制用户，而是为了避免在本地 SQLite 分析库和 1GB 级容器资源下制造不稳定体验。

## 4. Agent 应该暴露事实，不能替业务拍板

Runtime 提供工具、状态和 guardrail；模型判断下一步。产品不能把“我们希望模型怎么做”偷偷编码成固定 workflow。

但这不等于放任模型猜：

- 系统要提供足够结构化事实，例如 schema、样本、统计、候选 join、候选指标、歧义列表和确认记录。
- 用户没有授权时，核心业务口径不能静默默认。
- 人工确认不是打断体验，而是保护高风险结论的必要交互。

## 5. 默认路径必须实用

产品应优先优化真实用户的高频路径：

- 上传或导入数据后，用户能立即看到数据规模、表名、行列数、语义画像状态和错误原因。
- 连接数据库时，创建、测试、编辑、删除、导入都要有清晰反馈。
- 大表导入被截断时，用户必须知道当前分析基于受限快照。
- 没有配置 LLM 时，确定性 schema 和 SQL 分析仍应可用。

## 6. 报告是交付物，不是运行日志

最终报告应服务阅读和决策，而不是复述 Agent 做过什么。

报告里应该出现：

- 业务问题和结论
- 数据范围、数据期间和口径假设
- 关键图表与计算依据
- 风险、歧义和需要用户确认的事项

报告里不应默认出现：

- 工具调用流水账
- 模型自我评价
- 没有业务意义的中间状态

## 7. 工程边界要帮助产品长期演进

当前系统的关键边界要继续保持清晰：

- 元数据库负责身份、工作区、会话、任务和数据源事实。
- session analysis SQLite 负责当前会话的可复现分析快照。
- 对象存储抽象负责文件和报告产物。
- Agent runtime 负责工具调用循环、状态暴露、压缩、审计和交付边界。
- 前端负责展示状态和收集确认，不承载隐藏业务判断。

如果新功能会混淆这些边界，应先重设设计，而不是用兼容胶水继续堆。

## 8. 判断一个功能是否值得做

新增功能至少应通过这些问题：

1. 它是否减少用户从数据到可信结论的时间？
2. 它是否降低口径、权限、数据规模或可复现性的风险？
3. 它是否让用户更清楚当前分析基于什么数据和假设？
4. 它是否能在没有完美 LLM 输出时仍保持可用？
5. 它是否能被测试、审计和回滚？

如果答案主要是“看起来更像 Agent”或“展示我们技术很酷”，默认不做。
