# Agent Runtime 实践经验

更新日期：2026-06-22

本文档合并了原来的 site draft 和长篇经验文档，只保留对本项目仍有指导价值的实践。

## 1. 不要把 Agent 做成隐藏工作流

系统只提供目标、工具、状态和边界。不要把“先查 schema、再写 SQL、再画图、最后报告”编码成固定路径。复杂任务需要模型自己判断探索、提问、委派和收尾顺序。

## 2. 观察工具优先于提示补丁

模型表现不稳时，优先检查是否缺少事实观察面，而不是继续加系统提示。`state_session_sources_inspect`、`state_semantic_profile_inspect`、`state_report_inspect` 这类工具应返回事实，不替模型下判断。

## 3. 结构化状态是脚手架

Working memory、goal tree、report block tree 的价值是可观察、可恢复、可校验。它们不是强制规划阶段，也不应该规定报告章节顺序。

## 4. Guardrail 只拦不可交付结果

Guardrail 应保护边界，例如非法 SQL、缺失 chart 引用、结构损坏的报告、绕过 CSP 的脚本。它不应该告诉模型下一步怎么做。

## 5. 长任务先治理上下文

长任务失败常见原因不是模型突然变弱，而是历史里低价值内容太多：

- 大段报告正文反复回灌。
- 图表 option 或查询结果过长。
- 状态每轮自动注入。

优先做压缩、摘要、按需观察和事实沉淀。

## 6. Delegate 是边界工具

只有当子任务边界清晰、工具权限可裁剪、结果回流明确时才使用 delegate。不要把多 agent 当作表演式并行。

## 7. Trace 是调优依据

调 prompt 前先看 trace：

- 哪些工具结果撑大了上下文。
- 哪一轮开始重复或漂移。
- 哪类状态被重复注入。
- guardrail 触发前发生了什么。

很多“模型问题”最终是工具契约、状态设计或历史保留策略问题。

## 8. 工具契约要像 API 文档

工具描述可以详细，但必须是契约：

- 做什么。
- 何时适用。
- 何时不适用。
- 读写哪些状态。
- 返回哪些结构化事实。
- 有哪些限制和失败条件。

不要在工具描述或返回值里写下一步建议。
